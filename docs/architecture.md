# Architecture

Ember is a single C23 library. Everything between the bytes of a page and the pixels on screen is Ember's own code, on top of
SDL3 (windows, input, files, threads, GPU through SDL_gpu), SDL_image (JPEG and GIF), kb_text_shape (shaping), SheenBidi
(bidirectional text), and, for networking, SDL3_net and mbedTLS.

## Modules

Each directory under `src/` is a module, built as an object library `ember_<module>` and linked into `libember`. A module
lists the modules it depends on in `src/<module>/deps.txt`; CMake checks that the dependency names exist. The public API
(`include/ember/`) is implemented by `embed`. Internal symbols are `embi_*` and are hidden in a shared build.

| Module | Role |
|---|---|
| `base` | Allocation, arenas, strings, atoms, hash maps, base64, LZ decompression, the monotonic clock, logging. |
| `num` | Number parsing and formatting shared by the CSS and JavaScript front ends. |
| `codec` | DEFLATE and zlib inflate, Brotli, WOFF and WOFF2, sfnt table access. |
| `jslex` | The JavaScript lexer. |
| `js` | The JavaScript engine: parser, scope analysis, bytecode compiler, interpreter with inline caches, object model with shapes, garbage collector, RegExp, ES modules, and the built-ins (Array, Promise, Proxy, typed arrays, BigInt, Date, Intl, ...). |
| `dom` | The document tree: nodes, attributes, events, mutation records, interned names. |
| `html` | The HTML tokenizer, tree builder, fragment parser and serializer, and input byte decoding. |
| `css` | The CSS tokenizer and parser, selectors and matching, the value parser for every property (generated database `props.txt`), `calc()`, colors, shorthands. |
| `style` | The style engine: flattening sheets into rules, the cascade, computed values, media and container evaluation, incremental invalidation, the user agent sheet (`ua/html.css`), `@font-face` parsing. |
| `font` | Font file parsing: sfnt and TrueType collections, outlines (glyf, CFF, CFF2), variations, colour tables, bitmap strikes. |
| `text` | Font registry and matching, system font index, shaping, line breaking support, bidi, glyph drawing, the bundled default font. |
| `layout` | Box tree construction, block, inline, float, flex, grid, table and positioned layout, hit testing, transforms, clip paths, and incremental relayout. |
| `anim` | Timing, keyframes, interpolation and the animator for CSS animations, transitions and the Web Animations API. |
| `paint` | Builds the display list from the layout fragments, with stacking contexts, layers, scrolling, damage between lists, and incremental list updates. |
| `gpu` | The renderer on SDL_gpu: one ubershader pipeline for boxes, gradients and images, outline rendering of glyphs and paths (Slug algorithm), glyph and image atlases, effects (blur, filters, blend modes), layer pool. |
| `image` | Image decoding (own PNG decoder, JPEG and GIF through SDL_image), EXIF orientation, an image cache with a byte budget, GIF frame clock. |
| `canvas` | Canvas 2D (optional, `EMBER_CANVAS`). |
| `svg` | SVG parsing, geometry, painting, SVG images (optional, `EMBER_SVG`). |
| `loader` | URL parsing and IDNA, MIME sniffing, encodings, `data:` URLs, Blob, Fetch, streams, structured clone, the module host and import maps, `localStorage` storage, random numbers. |
| `net` | The network service (optional, `EMBER_NET`): HTTP/1.1, TLS, connection pool, redirects, cookies, content decoding, WebSocket, EventSource, the host allowlist. |
| `platform` | Input semantics that are not DOM: hit-point handling, focus, pointer and keyboard state, key mapping, text editing, the clipboard, cursors, and the answers for `:hover`, `:focus`, `:checked`, `:valid` and similar. |
| `bindings` | The JavaScript-visible DOM and Web APIs: glue generated from WebIDL (`idl/*.webidl`, generated by `tools/idlgen` into `gen/`), the hand-written implementations (`impl_*.c`) and the scripts written in JavaScript (`js/*.js`: animation, streams, XMLHttpRequest, CSS namespace, stylesheets). |
| `embed` | The embedding layer: runtime and view objects, document loading, the frame and event loop, timers and tasks, the realm and script glue, input dispatch, resource handlers and mounted directories, network loads, window handling, and the public API. |

## From bytes to pixels

1. **Bytes in.** `emb_view_load_url` or `emb_view_load_html` takes a document. URLs resolve through a resource handler,
   the built-in `data:` and `file:` loaders (the latter only inside allowed directories) or the network service (`embed/resource.c`,
   `embed/netload.c`). The `loader` module parses URLs and sniffs the encoding; `codec` decodes compressed content.
2. **HTML parsing.** `html` tokenizes and builds the DOM (`dom`). A script element pauses the parser, runs through
   `embed` and the JavaScript engine, and the parser resumes, as the HTML standard describes. Subresource loads (styles, images,
   fonts, scripts) start as the parser finds them.
3. **Style.** `css` parses style sheets, and `style` flattens them into rule entries (with `@media`, `@supports`, `@layer`
   and nesting resolved), matches them against elements, runs the cascade and computes values. Invalidation is selective:
   `style/inval.c` works out from the selectors which elements a changed class, id, attribute or child list can affect, and
   only those are restyled.
4. **Layout.** `layout` builds a box tree from the styled DOM and lays it out into fragments: block flow, inline formatting
   (with `text` for shaping, bidi and line breaking), floats, flex, grid, tables, absolute, fixed and sticky positioning.
   Text measurement comes from the font and text modules.
5. **Paint.** `paint` walks the fragments and records a display list: fills, borders, images, gradients, text runs,
   decorations, with clips, transforms and stacking contexts, and layers for opacity, filters, masks, blend modes and 3D planes.
6. **Damage.** The new display list is compared with the previous one (`paint/damage.c`), by stacking context. The
   differing regions become damage rectangles, so a frame redraws only what changed. Layers that did not change are
   kept as cached textures.
7. **GPU.** `gpu` turns the display list into batched draws on SDL_gpu: boxes, gradients and images go through one
   ubershader pipeline with instancing; text and paths are drawn from their outlines on the GPU rather than from a glyph
   bitmap, so they stay sharp under scale and transforms. The shaders are written in Slang (`shaders/`), compiled by `slangc`
   at build time to SPIR-V, DXIL or MSL, and embedded with `#embed`.
8. **Present.** A windowed view presents its swapchain; an offscreen view leaves the frame in its own texture
   (`emb_view_texture`) for the host to composite.

JavaScript and the DOM bindings run between these steps: scripts change the DOM, and the next update restyles, relayouts and
repaints what changed. `requestAnimationFrame` callbacks, CSS animations and transitions run on a frame clock that each update
advances; timers and posted tasks run on the view's event loop (`embed/loop.c`).

### Incremental updates

- **Style:** only elements marked by invalidation are restyled.
- **Layout** (`layout/incr.c`): after a change, the style engine hands over the set of changed elements. If nothing that
  layout reads changed, fragments stay. If only paint properties changed (color, background, opacity, transform), boxes
  keep their fragments and are only marked for repaint. If layout inputs changed, the box subtree of the nearest enclosing
  block container that can be rebuilt on its own is rebuilt and spliced in, and the affected ancestors are laid out
  again from recorded constraint spaces instead of the whole document.
- **Paint** (`paint/incr.c`): after a paint-only change, the stacking contexts that hold the changed elements are rebuilt
  and spliced into the previous display list; anything it cannot do exactly falls back to a full rebuild.
- **Scrolling:** a pure scroll reuses the display list and moves the viewport.
- **GPU:** damage rectangles and cached layers limit the pixels redrawn.

## Threading

The API is single-threaded: a runtime and its views are used from one thread (see the
[embedding guide](embedding.md#threading)). Ember uses its own threads only for work that does not touch the DOM:

- the network service (all socket work; the results are posted back to the view's thread);
- the system font index build;
- preparation of the JavaScript realm before the first script, and its release;
- GPU start-up: creating the renderer and the view texture in a windowed view, compiling pipelines that the first frame
  does not need;
- layout of very deep documents on a thread with a larger stack (the call waits for it);
- memory pre-faulting of arena blocks, and parsing the user agent sheet at runtime creation.

`emb_view_post_task` and `emb_resource_complete` are the entry points for the host's own threads.

## Memory and size

- Memory is allocated through SDL (`SDL_malloc`), wrapped by `base` (`embi_alloc`), and tracked in totals. Most data lives in
  arenas (per document, per layout, per frame) and is freed in bulk.
- The JavaScript heap is a non-moving mark-sweep collector with a conservative scan of the C stack and lazy sweeping;
  there is an optional generational mode.
- Style, layout and display lists use compact records; the idle memory per view is a design goal (below).
- The library size is controlled by the size configuration (`EMBER_MIN_SIZE`) and by build-time switches for canvas, SVG, the
  default font and the network stack (see [Building](building.md#size-build)). Assets that are embedded in the library
  (shaders, prelude scripts, the UA sheet, the Brotli dictionary, RegExp tables, root certificates) can be stored compressed.

## Budgets

These are design goals, checked by CI and by `tools/bench/bench_view`:

| Budget | Goal |
|---|---|
| Library size | Under 3.2 MiB, stripped, excluding SDL3, in the size configuration (`EMBER_MIN_SIZE=ON`, `EMBER_NET=OFF`, canvas, SVG and default font off) |
| Memory | Under 15 MB per idle view |
| First paint | Under 20 ms from runtime creation to the first submitted frame |
| Frame rate | A steady 60 fps for scrolling and animation |

How they are checked:

- CI builds the size configuration with GCC 15 and reports its stripped size. The gate against `tools/bench/budget_baseline.txt`
  is not enabled yet because the GCC 15 baseline line has not been recorded; the step only reports until it is added.
- `bench_view` loads a page, and with `--app` an unmodified React TodoMVC build, and prints first paint, scrolling frame times,
  the heap per view and the library size against the budgets. The heap per idle view of that app is recorded in the baseline
  file as 6,281,550 bytes, and CI fails if it grows by more than 5%.
- The baseline file also holds timings from a Linux software-rendering machine (first paint of about 94 to 98 ms, taken under
  heavy load). The first-paint goal is therefore a goal, not a measured result of the current preview; the numbers depend heavily
  on the GPU driver start-up time.
- `bench_anim`, `bench_layout`, `bench_style`, `bench_render` and the JavaScript benchmarks in `tools/bench/js` measure the
  individual stages. See [Testing](testing.md#benchmarks).
